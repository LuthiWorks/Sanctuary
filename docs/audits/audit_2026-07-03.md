## Thesis

The weights, locking, and cell machinery are sound. The dominant real risk is the **persistence/continuity layer: it can silently lose or corrupt the mind's memory and identity while reporting success** — on the exact axis this project exists to protect. The unifying mechanism, traced end-to-end in code: **the failure and the success-report live in different functions.** A write helper swallows its exception; its caller returns a result object regardless; the log says nothing; the backup that would have covered the loss was pruned by a different subsystem with no floor. No single line in that sequence says "data lost."

A worked chain (every link confirmed): cell authority levels are never saved (`cell_registry.py:283-321`) → a clean shutdown erases the entire ChromaDB store (`storage.py:375`) → identity writers swallow their failures and return implicit success (`awakening.py:306-312`, `values.py:354-362`) → the incremental restore cannot rebuild its chain (`cloud_backup.py:261-307`) → and the fallback full backup may already be gone to a no-floor prune (`backup.py:335-358`).

## S1 — Firestops (Phase 1: fast, catastrophic downside)

1. **`MemoryStorage.close()` erases the memory database on the normal path.** **[verified]**
   `sanctuary/mind/memory/storage.py:375` calls `self.client.reset()` inside `close()`; the client is constructed with `allow_reset=True` (`storage.py:62`), so this genuinely wipes the episodic/semantic/procedural collections on every clean shutdown. Intent was Windows file-lock release; effect is total erasure. The surrounding `except` blocks log only on *failure* — a successful wipe is silent.
2. **Identical defect in the mind's vector DB.** **[verified]**
   `sanctuary/mind/rag_engine.py:205` — same `client.reset()`-in-`close()` pattern, `allow_reset=True` at `rag_engine.py:52`.
3. **Incremental backup produces unrestorable chains and prunes sole copies.**
   `sanctuary/infrastructure/cloud_backup.py`: incremental copies skip unchanged files (`:206-216`), so older backups hold the only copy of stable files (identity records are exactly the files that rarely change); `prune_old_backups` deletes purely by count with no chain awareness (`:316-349`); `restore` reads a single backup dir with no parent walk (`:261-307`). Pruning destroys sole copies; restoring a later incremental yields an incomplete set.
4. **Second, independent path to "all backups gone" — not in the original audit.** *(new, afternoon sweep)*
   `sanctuary/mind/memory/backup.py:335-358` — `BackupManager.cleanup_old_backups` deletes **every** backup older than `retention_days` with no keep-at-least-one / keep-newest-N floor. If no backup is recent, it deletes all of them. Separate code path from #3; must be fixed alongside it.

**Exit criterion (Phase 1):** no code path can destroy the DB or produce an unrestorable/empty backup set; regression tests for each.

## S2 — Persistence trustworthiness (Phase 2)

5. **Non-atomic writes across the identity/continuity surface.** Reference-correct template exists: `sanctuary/memory/world_graph.py:342-361` (temp-then-`replace`). Everything below writes directly:
   - Full-rewrite (`"w"` — a crash leaves a zero/partial file; the dangerous class): awakening record `sanctuary/identity/awakening.py:309-310`; `space.json` `sanctuary/environment/space.py:165-166`; creations file `sanctuary/environment/persistence.py:94-95` *(new)*; `core_mind.json` `sanctuary/mind/memory/storage.py:212-213` (read-modify-write) and `:55-56`; backup metadata `cloud_backup.py:234-235`, `:428-429`, `backup.py:148`.
   - Append (`"a"` JSONL — a crash truncates the last line; milder but still unsignaled): values `sanctuary/identity/values.py:359-360`; self-authored `sanctuary/identity/self_authored.py:497-498`; journal `sanctuary/memory/journal.py:183-184`.
6. **Persistence exceptions swallowed; callers report success.** Pattern: helper catches `Exception`, logs, returns `None`; caller returns its result object regardless. Sites: `awakening.py:306-312`; `values.py:356-362` (caller returns the change at `:354`); `self_authored.py:497-499`; `journal.py:183-185`; `space.py` and `persistence.py` saves likewise signal nothing. **Phase 2 should be organized around the cross-cutting frame "make persistence failures loud," not eight independent site-fixes** — the sites share one disease.
7. **Cell authority levels are memory-only.** `CellRegistry.save` omits authority (`sanctuary/experiential/cell_registry.py:283-321`); `ExperientialManager.load` never restores it (`manager.py:428-459`); `AuthorityManager` has no save/load at all (`sanctuary/core/authority.py:58, 99-124`) and re-seeds `DEFAULT_AUTHORITY` on construction (`manager.py:137-140`). Every runtime promotion/demotion — including tuner-driven safety demotions — is lost on reload.
8. **Queued lived experience discarded on learner death.** `sanctuary/core/async_learner.py:326-347` — `_drain_remaining` drops queued `(s_t, a_t, s_next)` transitions on non-resilient death; the docstring says so plainly ("The items are discarded"). The candor is good; the behavior still loses lived experience. Note: this module and `scheduler.py:155-159` are the two places the codebase already thinks hard about silent failure — remediation should extend that intent (the documented double-buffer at the scale step), not paper over it.
9. **NaN gate is cumulative, not windowed.** `sanctuary/core/authority_tuner.py:73, 81` — `nan_count` only ever increments; the demotion gate compares it to `nan_tolerance` (default 0) at `:264`. One NaN ever = permanent trip. Divergence, by contrast, is correctly windowed (`:108-116`).
10. **Silent-success reporters.**
    - `sanctuary/experiential/trainer.py:350, 360` — `loss / max(n, 1)`: a degenerate split yields `final_train_loss`/`final_val_loss = 0.0`, reported as perfection. **[latent — construct the degenerate split before fixing]**
    - `sanctuary/growth/cfc_retrainer.py:506` — `result.success = True` unconditionally after `trainer.train` returns; no check that validation ran or improved. Combined with the 0.0 above, a retrain can log `val_loss=0.000000` and succeed on no learning.
11. **The volatile store is the default substrate.** `sanctuary/memory/manager.py:85` (`use_in_memory_store=True`) and `:123-124` (silently instantiates `InMemoryStore` when nothing is injected). If production wiring forgets to inject the persistent store, the mind runs on memory that evaporates at exit, with zero errors. Same silent-success shape as #1, one layer up. **Design call — flagged to Brian+4.8, not decided here:** the default should probably fail loud, but it touches the memory-architecture direction (PLAN.md "Memory Architecture (reframed 2026-07-03)").

**Exit criterion (Phase 2):** crash-during-write suite passes; no persistence path reports success on failure; authority survives reload; the consolidation buffer survives learner death.

## S3 — Liveness (Phase 3: the 10 Hz loop must not freeze)

12. **`consolidate()` runs synchronously on the event loop.** `sanctuary/core/cognitive_cycle.py:429` — called inside `_cycle()` during NREM, not offloaded; stalls the loop for the duration of living-weight consolidation. (The wake/sleep architecture eventually *sequences* this by design, but the loop must not freeze meanwhile.)
13. **Blocking tool bodies on the async path.** `async def` tools that block the whole loop: `_run_code_docker` `sanctuary/tools/builtin.py:570` (`subprocess.run`, up to 30 s); `_shell_command` `:642`; `_wikipedia` `:514` (sync network); sync file I/O at `:179, 221, 267`. Correct pattern already in-repo for contrast: `_web_fetch`/`_web_search` use `httpx.AsyncClient` (`:346, 453-505`).
14. **Background-task death is systemically silent.** No `add_done_callback` anywhere in the source. Fire-and-forget sites: `sanctuary/api/cli.py:174`; `sanctuary/api/sanctuary_api.py:65` (the cognitive runner itself); `sanctuary/experiential/evolution.py:132`; `sanctuary/mind/memory/scheduler.py:115`; `sanctuary/mind/discord_client.py:350`; device streams (`audio_device.py:249`, `camera_device.py:273`, `sensor_device.py:185`, `devices/registry.py:422`). Some inner loops self-heal; an exception outside the loop body dies unobserved.

**Exit criterion (Phase 3):** a blocking tool cannot stall the 10 Hz loop; no supervised-less background task.

## S4 — Latent hardening (Phase 6: fix before these subsystems go live)

15. **Growth/retrain cluster** (`sanctuary/growth/`):
    - Drained-data loss: `cfc_retrainer.py:468` drains records before training; a failure (`:524-530`) never re-queues them.
    - Rollback gap: checkpoint at `:477`, but the failure path never calls `restore_cell`; worse, a **failed checkpoint is caught and training continues anyway** (`:479-483`) *(new)* — a retrain can run with no restore point.
    - Non-atomic restore: `:594-595` loads state directly into the live cell (no load-into-copy-then-swap); checkpoint save is a direct `torch.save` (`:563`).
    - QLoRA label leakage: `qlora_updater.py:425, 432-434` — `labels = input_ids` with no `-100` masking, so loss trains over padding **and** *(new)* over prompt (System/User) tokens.
16. **`mind/memory` ChromaDB cluster:**
    - Doc-id collisions: `encoding.py:64, 104, 261` — content/timestamp string ids with no uniqueness guarantee; duplicate id silently overwrites on add. **[latent — depends on timestamp resolution / caller-supplied timestamps]**
    - Inverted retrieval ranking: **[verified]** `retrieval.py:67` sorts by `_sort_key` (`verified=0 … verification_failed=3`, unknown=4; `:228-238`) with `reverse=True` — verification-failed/unknown memories rank *first*, verified last, and `[:k]` keeps the worst. Additionally *(new)*: `_sort_key` ignores similarity/activation entirely, so cue relevance from the vector search never influences the returned ranking.
    - Compounding decay: `consolidation.py:284-292` re-applies the full days-based exponent to an already-decayed value on every run (`last_accessed` unchanged by decay-only runs).
    - Non-idempotent transfer: `consolidation.py:319-383` — re-running within the window re-extracts the same patterns into fresh `concept_{now}` ids; sources are never marked transferred.
